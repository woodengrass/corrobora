# 04｜候選方法：有條件的診斷經驗轉移

[索引](../README.md) · [研究假說](01-research-questions.md) · [評測](05-evaluation-protocol.md) · 2026-10-02

工作名稱：Conditional Diagnostic Experience Transfer（CDET）。尚未實作、未證實有效或原創。此文件把候選方法寫到能被實作、比較與否證，不要求全部模組都留下。

## 1. 先決條件

P2 必須先證明有可重現的重用傷害、診斷浪費或跨設計缺口。若強模型使用原始歷史或普通筆記已經同樣有效，就不進行大型方法開發。

方法不需要完整 Minecraft 因果圖，也不要求每次失敗都有唯一原因。它主要幫助 Agent 選擇「直接重用、補一個檢查、調整舊程序、重新調查或停止」。

## 2. 三種資料分開

| 物件 | 內容 | 權限 |
| --- | --- | --- |
| experiment_record | 初始條件、事前預測、操作、觀察、成本、artifact hashes | Runner 追加，不可被模型覆寫 |
| diagnostic_experience | 可重用測試、前提、解釋、適用範圍、反證與修訂 | Agent 可提案；revisioned，保留來源 |
| working_state | 本次角色對應、候選原因、計畫、未知事項 | 可改寫；不自動升級為永久事實 |

「某次輸出低」是觀察；「下游容量造成輸出低」是待檢驗解釋。失敗不直接變成永久禁令。

## 3. 最小經驗格式

```text
experience_id / revision_id / parent_revision_id
source_task_ids / source_experiment_ids
symptoms / module_roles / required_observables
hypotheses_distinguished
preconditions: predicate, supporting_refs, contrary_refs, status
experiment_template: bindings, intervention, measurement, limits
predictions: hypothesis_id, expected_outcome, tolerance, unknowns
scope: environment_version, design_conditions, load_conditions
supported_scope / contradicted_scope / unresolved_scope
suggested_repairs / repair_validation_refs
tool_artifacts: hash, dependencies, permissions, validation_refs
measured_costs / estimated_costs
```

前提狀態先用「有支持、未知、已知不符」，不把模型語氣轉成真實機率。多條來自同一實驗或轉述的筆記不是多份獨立證據。來源條目應去重到原始 run，避免重複支持把信心灌高。

程式可執行、引用存在、預測吻合與修復有效分開。正式驗證只對特定版本與條件有效，不提供可由 Agent 自行打勾的全球 verified 欄位。

## 4. 取回經驗與角色對應

按症狀、可觀察狀態、模組作用與操作條件搜尋，而非只按農場名稱。所有組仍可使用原始歷史；結構化經驗是額外候選，不是排他入口。

將舊程序中的入口、出口、儲存端等角色綁到新世界的觀察位置。這種對應也可能錯，必須有可檢查依據；不得讀 benchmark 私有模組標籤。找不到合適對應就從原始證據重新調查。

檢索數量、排序、上下文長度在 dev 階段固定。若引入新 embedding 或 reranker，另做對照，不能把檢索品質差異全稱為推理方法效果。

## 5. 適用性檢查的決策

硬限制如權限、版本禁用與預算由工具層執行，不因移除方法 gate 而關閉。

對研究前提：

- 已知不符：禁止照原樣當結論使用；可改寫成新候選測試，但須重新驗證。
- 未知且會改變修復決策：考慮有限成本的檢查，或保留多個解釋。
- 未知但不影響目前行動：不必為完整性做無價值測試；明記仍未知。
- 有支持：允許將舊測試列入候選，不直接認定這次故障相同。

Gate 不應變成「每條筆記都完整重驗」。停止檢查的時機、檢查成本与省下的錯誤修改要一起評估。必要時寧可放棄重用，或用可回復的局部修復驗證。

## 6. 產生候選假說與實驗

Agent 提出有限數量的不同解釋，每個候選實驗預先記錄：改什麼、量什麼、每個解釋預期看到什麼、哪些因素固定、成本和風險、不同結果會如何改變下一步。

允許區間、分類與 unknown，不強迫捏造精確流量。假說要有實質差異，不能把同一解釋改寫多遍來提高分歧分數。必須留有「目前候選都不對／量測或對應出錯」的出口。

模型可能提出共同錯誤的假說；因此一致預測不能證明正確。候選池失敗、對應失敗、選擇失敗與結果解讀失敗分開分析。

## 7. 最小可實作的選擇策略

先排除不可執行、違規或超預算的測試。再優先選擇不同可觀察結果會導致不同修復決策的測試；相近候選以預估成本比較。不要把單純重複整台農場的低輸出，誤當作對所有原因都有診斷力。

可用下列分歧啟發式作第一個候選，而非宣稱新資訊理論：

`D(e) = 可被實驗 e 的預測結果區分的假說對數 / 目前不同假說的總對數`

兩個預測區間重疊或任一 unknown 時，不計入已可區分。區間不重疊只是所提假說下的判準，不保證真實噪聲下可分。容忍範圍要經 dev 校準。

只有一個假說時，選可反駁它的測試或擴充解釋，不把分母零當高分。假說數量與生成預算固定，避免靠列很多變體抬高分數。

排序至少比較：最便宜合法測試、固定順序、隨機合法測試、強模型自由選擇。先不把未校準分數稱為 expected information gain，也不宣稱具有貝葉斯最優性。只有建立可校準的概率模型後，才另測真正的期望資訊／決策價值。

## 8. 執行後如何修正？

先提交預測 hash 再運行。結果不符時檢查操作是否合法、工具是否成功、觀察位置和條件是否正確；不要第一時間推翻全部領域知識。

可選動作是保留、限縮適用條件、建立另一情境分支、修改程序、標記待重驗或淘汰候選。關聯只表示「值得重查」，不表示下游結論必然為假。沒有可靠依賴時用保守局部回歸，不先建大型治理圖。

修復後在完整農場與未受影響控制情境驗證。修好了設計只能證明修改有效，不一定識別唯一機制。不能辨識時保留解釋集合或 unknown，並報下個可能有用的測試。

## 9. 經驗如何改善下一次設計？

同一診斷程序也可用於設計前容量檢查、模組驗收與選擇。需記錄它用於初始設計、故障診斷或後續驗證中的哪一階段。

完整藍圖重用、局部模組重用、診斷實驗重用分開。它們都可能實用，但不能用照搬成功藍圖證明新機制理解。第一個方法研究以診斷／測試轉移為中心，從需求設計作獨立擴展。

## 10. 必須做的消融

| 比較 | 可區分的解釋 |
| --- | --- |
| 同結構化內容，有／無額外 gate | 格式整理與適用性檢查誰在起作用 |
| gate 開關 × 選擇策略開關的 2×2 | 檢查、選測試與交互作用 |
| 固定假說／實驗池，只換排序 | 更好的生成與更好的選擇不是同一件事 |
| 普通筆記、原始歷史、條件式經驗 | 是否特殊格式真的必要 |
| 局部重驗與完整重調查 | 成本下降是否以漏修／誤修為代價 |
| 同一套歷史，不同模型內完整比較 | 效果是否被較強模型吸收 |

共享的證據紀錄與安全限制各組都有；若只有處置組被要求詳寫預測，其额外 token 與行為改變也是處置成本。正式實驗需固定共同的最低可評測輸出，避免暗中不對稱。

## 11. 既有研究的邊界

主動選實驗、記憶抽象、驗證後重用與狀態修正都有先例，見 [08](08-related-work.md)。CDET 現在是工程化候選組合，不足以僅憑此文件聲稱新演算法。方法貢獻取決於具體不同的決策與公平實驗；若最終只有現象和新測試集，就據實定位。
