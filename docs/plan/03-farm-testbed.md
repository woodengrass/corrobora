# 03｜完整農場測試環境與量測

[索引](../README.md) · [系統](02-system-and-stack.md) · [P0 工作表](../experiments/p0-first-farm.md) · 2026-10-02

本文件是待實作契約，不代表 Minecraft 內建同名工具，也不代表已取得農場藍圖。

## 1. 什麼才算完整農場？

必須由宣告的合法輸入與遊戲機制持續產生目標物，經必要的收穫／處理／運輸流程到達指定輸出端。單獨點燈、孤立收集模組、直接注入成品都不算完整農場。

`repair_optimize` 提供起始農場，要求在限制內恢復或提高功能。`design_build` 只提供需求、允許資源、區域與來源資料，Agent 自行提出完整設計。兩者分開統計，禁止混成一個自主設計成功率。

人工 reference 只證明任務可行，不宣稱最優；不作為 Agent 的隱藏答案。主研究優先固定底層遊戲規則，改變布局、模組組合、負載或合法操作條件。真實版本遷移與人為改規則另列實驗。

## 2. 第一批選題原則

先選 2–3 類候選完整農場，實際類別由來源、可行性、測量成本及機制差異決定。可先評估自然生長作物的完整收穫與收集鏈，但不能預先斷言它一定會有下游容量瓶頸。

候選必須有：可理解的正常設計、穩定量測窗口、可重設狀態、不同原因的實測變體，以及可接受的執行成本。若產量低到看不出差異，應加長窗口、選另一個合法設計或換候選；不要偷偷提高 randomTickSpeed 後還宣稱原規則。

當 reference 的到達速率明顯低於下游容量時，不要硬製造「自然的收集瓶頸」。可宣告合法的出口限制或負載條件，但要把受控故障、天然缺陷和條件變化分開標示。

## 3. 公開與私有 task manifest

| 公開欄位 | 內容 |
| --- | --- |
| 身分 | task_id、revision、task_mode；名稱不洩漏故障 |
| 需求 | target_items、正式輸出端、品質門檻、允許輸入、材料／空間限制、禁止動作 |
| 環境 | 遊戲版本、server hash、loader／mods／JDK、設定 hash、世界快照 |
| 運行條件 | gamerules、難度、時間／天氣策略、random tick 設定、玩家位置、區塊與實體載入範圍 |
| 觀察介面 | 可讀狀態、事件粒度、資料長度與查詢成本，不提供私有模組答案 |
| 時間與預算 | 預熱、量測窗口、每次與累計 ticks、模型與工具限制 |
| 來源 | 自建／改編、作者、URL／版本、授權及公開限制 |

私有 manifest 保存 design_lineage_id、family／機制組合切分、研究者的故障標註、參考分布、保留 seeds 與測試条件。公開規格應揭示任務要求與允許的條件範圍；不能藉「hidden」在驗收時換成未宣告的任務。

Agent 若免費得到人工標好的模組圖或故障位置，必須標成 oracle-assisted，不能混成自主診斷。

## 4. 待實作工具

| 操作 | 契約 |
| --- | --- |
| create_episode | Runner 建立隔離世界；Agent 不選保留測試配置 |
| inspect / query_events | 讀允許區域的方塊、容器、實體與事件；記時間、範圍及成本 |
| apply_patch | 驗證區域、材料、狀態 revision 與操作限制；保留修改前後身分 |
| advance_ticks | 推進有限 ticks；回報實際 ticks、完成狀態與牆鐘時間 |
| checkpoint / reset | 封存可還原狀態與限制；失敗時從乾淨世界重建 |
| fork_diagnostic | 在隔離副本進行宣告的注入、隔離或模組壓力測試 |
| submit_design | 凍結結構與必要設定，由另一個世界獨立重播驗收 |

工具允許程式化建造與局部修改，不包含無限制主機 shell、任意 server command、改評分器、讀隱藏標籤。生成的程式透過這些工具工作，不直接取得世界檔案與伺服器程序的寫入權。

MCP 只是可選包裝，同一應用服務也可供一般 function calling 使用，避免為不同模型維護兩套世界規則。

## 5. 三個世界要隔離

建造世界供 Agent 觀察與修改；診斷副本允許被標記的模組級干預；正式驗收世界從乾淨初始條件重播凍結設計。

診斷副本可用固定輸入測容量，但注入物品、建立的實體、修改的遊戲規則不能回灌正式驗收。由診斷副本選出的設計 patch 可以提交，仍須通過正常任務限制。

新世界重播要保留設計真正需要的方塊實體、合法初始種子／耗材、方向與設定，而不複製已積存的大量成品來提高分數。結構、初始合法物料與運行中庫存各自列入契約。

## 6. 產量不是隨便讀箱子差值

正式產出是量測期間由合法流程送達指定終端的淨新增目標物。需要排除初始成品、外部注入、重複跨邊界計數與診斷產物。

最簡單方案是專用、初始空白、Agent 不可直接寫入且不回流的終端，加上有來源的事件紀錄。若輸出容器會被取出或回流，單純期末減期初不足，必須額外計帳。事件擷取也可能漏掉轉換或合併，需用小型可算案例校準。

合法耗材、初始成熟作物、初始存貨與啟動瞬間的大量產出都要宣告。正式評測需觀察足夠的持續運行或多個窗口，避免一開始清掉預存產物就假裝長期高產。不能在本來不滿足守恆的轉換／掉落流程上硬套通用守恆公式。

每個 family 定義自己的 accounting：哪些事件代表生產、消耗、轉換、損失、積壓與正式交付；證據不足時不給高分。

## 7. 品質、時間與可靠性

主要條件是成功門檻加可行性約束，例如最低合法輸出、不能持續累積故障、材料與區域合規。產量、可靠性、面積、資源與 lag 分開報，不臨時拼出有利於方法的加權分數。

主量用 items／simulated ticks。若換算每模擬小時，明列換算規格；實際每小時產出則使用牆鐘時間，不能忽略 TPS 下降。模型等待時間、server 執行時間與總耗時也分開。

固定預熱與量測窗口，在 P0 用 reference 的多次運行校準；正式驗收使用未參與設計選擇的重跑條件。低於自然波動的小幅上升，不直接宣稱改善。

上游產出、下游收集與實體處理可能相互影響。隔離某模組會改變負載，因此局部測試只能支持有限結論；每次修復最終回到完整農場驗收。

## 8. 重置、亂數與觀察成本

同一 world seed 不等於相同軌跡。需考慮 RNG、實體 AI、scheduled ticks、block entities、容器、時間、載入狀態與玩家／bot。能完整捕捉什麼由 adapter 測試決定，未捕捉部分列為限制。

第一版寧可關閉測試服、由乾淨世界複製重啟，也不要承諾不存在的任意 tick 精確回滾。先確認這種重跑的變異，再優化熱快照。配對初始快照可減少部分差異，但不同動作之後不能假設仍共享同一串亂數。

一次觀察看多少區域、傳回多少 bytes、等待多少 ticks 都要記錄。較強工具可能直接暴露瓶頸；其權限在各組一致。影像、全世界掃描與逐 tick 詳細事件不是必然免費，也不必同時開放。

測量器可能改變效能甚至機制。用 reference 比較開關量測器的行為分布，量出額外成本；不能把感測器造成的差異誤判為 Agent 能力。

## 9. 提交與驗收回饋

開發期允許固定頻率的真實觀察與公開品質回饋；工程迭代不能完全沒有回饋。最終保留驗收的標籤、seeds 和完整診斷紀錄則不回到 Agent 的跨題記憶，也不作為研究者的調參資料。

若每題允許多次正式提交，次數與回饋內容在 dev 階段固定且計入預算。反覆查詢同一 hidden evaluator 再挑最好版本，不叫獨立保留測試。

## 10. 環境驗收清單

在接模型前，用已知操作驗證：零產出、正常產出、出口阻塞、初始存貨、非法注入、重複事件、越界修改、快照失敗、取消與超時。重跑不能帶入上一輪物品或計數器。

Infrastructure failure、非法設計、未達標和無法診斷分開。重試政策事先固定；不得把模型失敗重新歸類成系統錯誤以改善成績。P1 交付 reference 分布、所有 sanity cases 與已知限制，不能只交一段成功影片。
