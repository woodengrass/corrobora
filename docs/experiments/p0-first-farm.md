## 1. 本次先完成什麼？

選一座完整農場，人工確認能運行，固定條件並取得可重跑的輸出紀錄；再判斷它是否適合用來測 Agent 的診斷與經驗轉移。

第一輪先不實作 CDET，不匯入全部舊語料，不訓練模型。可寫必要的計數／重置小程式，但不以搭建資料平台代替取得第一次有效實驗。

## 4. 公開任務草案

任務模式：`repair_optimize`，尚未接 Agent。

- 目標物：待填。
- 合法輸入及是否允許耗材：待填。
- 正式輸出端與初始庫存：待填。
- 建造／修改區域、材料與機制限制：待填。
- 允許的觀察與工具：待填，先保持各組一致。
- 禁止動作：直接注入成品、改計分器、讀私有故障答案、任意 server OP 或繞過工具写世界。
- 公開品質回饋與頻率：待定。
- 成功門檻：待 reference 量測後在 dev 定案，不預填理論最高值。

隱藏標註與最終驗收 seeds 另存於 Agent 不可讀的位置。本工作表之後若包含故障答案，也不能直接掛載給 Agent。

| 問題 | 待填答案 |

| 怎麼確認農場真的可持续產出？ | 待填：不是只收初始成熟作物或預存物品 |

## 6. 原因不同的候選變體

下表只是待驗證設計，不是已知可觸發的故障。初期挑 3–5 個有意義案例即可，不必湊齊分類。

| 變體 | 候選操作 | 需證明什麼 |
| --- | --- | --- |
| 正常控制 | 不改設計 | 重複分布可量測，不能把自然波動當故障 |
| 生產／收穫相關 | 待定合法局部修改 | 真的影響上游，不是計數器或載入狀態出錯 |
| 運輸／交付相關 | 待定局部設計差異 | 能觀察到實际損失或積壓，有獨立證據 |
| 下游限制 | 只有負載確實達到容量時才採用 | 不能在低負載農場硬宣稱收集瓶頸 |
| 誤導性相似 | 表面低產但原因與先前不同 | 不適用經驗的標籤有實測依據，不按 CDET 勝負決定 |

每個變體記 patch、正常對照、預期效應、實際效應、是否可逆、是否有多原因、是否屬人造故障。人工 reference 修復應能在新世界重播。

## 7. 第一批 sanity checks

- 零產出確實得到零，不會計入殘留或初始庫存。
- 正常輸出可與人工核對；相同事件不重複計數。
- 診斷副本的物品不能流回正式評分。
- 不合法注入／越界修改不能提高有效成績。
- 重置後沒有上一輪物品、實體或計數殘留。
- 逾時、崩潰與取消會保留 trace 和成本，不自動算成模型失敗或成功。

記錄每項實際測試日期、程式版本、結果與證據路徑；目前全部尚未執行。

## 8. P0 完成判斷

只有在來源限制清楚、正常版可運行、量測可核對且變異已觀察後，才進 P1。若沒有正常資料，就先解決農場／配置；若觀察不到有意義的不同原因，就調整候選，不把不成立的案例寫成 gold。

完成時附：公開 manifest 草案、私有標註位置、正常設計與 hash、逐次量測結果、候選變體、量測限制，以及是否值得進 P1 的理由。
